## 1. Explain the problem SAS solves (non-technical)

Dart Global Logistics runs its freight-forwarding operations through CargoWise, an ERP built for logistics companies — it tracks every shipment's paperwork, dates, and status. The problem isn't that CargoWise lacks the data; it's that nobody is *watching* it. A staff member only finds out a shipment is stuck when they happen to open that job in CargoWise, or when a client calls asking where their cargo is. Multiply that across hundreds of shipments and the only real strategy is "keep checking everything, just in case" — which wastes time on the shipments that are fine and still misses the ones that quietly went wrong.

SAS sits next to CargoWise, never writes back to it, and just watches. For every shipment it knows what *should* happen and by when (a milestone template — e.g. cargo ready → pickup → departure → arrival → delivery). Every day it compares what CargoWise actually shows against that plan, and only when something is missing, late, or out of order does a person hear about it — by email, batched so one person gets one digest rather than a stream of pings. Once CargoWise shows the milestone done, the alert clears itself; nobody has to remember to close it out.

## 2. What is CargoWise? Who was the client/stakeholder?

CargoWise is the ERP/TMS (transport & logistics management system) that freight forwarders use to run jobs end to end — bookings, shipment milestones, customs docs, billing. The client is **Dart Global Logistics**, a Sri Lankan freight forwarder, and CargoWise is their system of record; SAS is a monitoring layer built on top of it for them.

One honest technical note: `services/cargowise_service.py` authenticates with a username/password grant against `CARGOWISE_API_URL` and then pulls from a single endpoint, `{CARGOWISE_API_URL}/cargo-pickup-date`. That's a narrow, purpose-built feed (job number, consignee, transport mode, pickup date/status, stage description, a couple of AI-derived fields like `llm_cargo_pickup_date`) — not CargoWise's full native API surface. If a panel asks "which CargoWise API exactly (eAdaptor, Web Services, or a middleware someone built in front of it)," that's worth confirming with whoever owns the `.env` / integration before the viva — the code only tells you the shape of the feed, not what's serving it underneath.

## 4. Walk me through what happens end-to-end when a shipment milestone changes in CargoWise

This is the one place the brief oversimplifies — there isn't one linear "sync → alert" pipeline, there are four separate jobs that each own a slice:

1. **CargoWise pull** (`routes/sync.py` / `app.py:run_sync_job`). Fetches the feed, and for each shipment builds `shipments.milestones` (a jsonb column) via the field registry, then `upsert_shipment()`s it with `on_conflict='cargowise_id'` — this is also your idempotency mechanism (see Q7).
2. **Status recompute**, every 30 minutes (`services/status_recompute.py`, job `status_recompute`). Re-reads every `shipment_milestones` row's frozen `milestone_snapshot`, resolves each field's current value via `resolve_field_value()` (checks the milestone's own json group first, then a normalized alias, then falls back to a plain shipment column), and flips status to `completed` / `overdue` / `delayed` (out-of-sequence) / `pending`. It also resolves `after_previous_milestone` due dates once the prior milestone completes.
3. **Field Watch**, every 30 minutes at :05/:35 (`services/field_watch.py`). A narrower, separate signal: is an expected field late *and* does a plausible renamed version of it already exist unmapped in that shipment's `raw_json`? If so it writes a yellow `field_alert` and emails one central admin (new-only, so it doesn't repeat).
4. **Alerting.** Two mechanisms exist, and they're at different stages of being "live":
   - `services/sales_digest.py` / `operations_digest.py` / `super_digest.py` — these **are** scheduled (daily at 8:00 AM Sri Lanka time) and **do** send real emails: up to two per person (Overdue Alerts, Upcoming Reminders), sorted critical-first, straight off `shipment_milestones.due_date`.
   - `services/alert_engine.py` — the full per-rule engine (timing, fire conditions, recurrence, stop conditions, per-rule recipients, idempotent via `alert_fire_log`) that the Milestone Builder's Step 3 "Alert Rules" actually configures. **I checked and this module is not called from any Flask route or scheduler job in `app.py`** — it's complete, has its own test file, and matches the Evaluation Contract exactly, but it isn't wired to anything live yet. Worth being upfront about this rather than implying the builder's per-rule alert timing is already firing in production — right now the digests are what's actually reaching inboxes.

Auto-resolve happens implicitly: once CargoWise shows the field filled, the next `status_recompute` pass marks the milestone `completed`, so it drops out of the overdue/upcoming buckets the digests read from — no separate "close the alert" step needed.

## 5. Why a 15-minute polling interval? Why not webhooks? Why not 1 minute?

Careful here — the code doesn't actually poll CargoWise every 15 minutes. `app.py`'s scheduler runs the CargoWise pull on a **fixed cron: 00:00, 06:00, 12:00, 18:00 Sri Lanka time**, plus whatever extra one-off times an admin adds via `/api/sync/schedules` (each becomes its own `CronTrigger` job, `custom_sync_<id>`). Separately, `status_recompute` and `field_watch` run every 30 minutes to re-evaluate data that's already landed. There's also a leftover prototype, `sync/database_sync.py`, with a literal `SYNC_INTERVAL_MINUTES = 30` interval job — but it's never imported by `app.py`, so it isn't actually running.

So if asked "why 15 minutes," the honest answer is "we don't poll CargoWise every 15 minutes — we settled on four fixed daily pulls plus admin-configurable extra times, because CargoWise is queried through an authenticated API call that has a real cost per hit, and shipment milestones (pickup dates, customs docs) don't change minute-to-minute — they change over hours. Four fixed times plus the ability to add more balances freshness against not hammering the CargoWise integration." No webhook exists on the CargoWise side we integrate with, so push-based updates weren't an option; a 1-minute poll would multiply API calls ~360x over the current fixed schedule for data that mostly doesn't move that fast.

## 6. What happens if a sync job takes longer than 15 minutes and the next one fires? (`max_instances`, `coalesce`)

None of the scheduler jobs in `app.py` set `max_instances` or `coalesce` explicitly, so they run on APScheduler's defaults: `coalesce=True` and `max_instances=1` per job. In practice that means: if `run_sync_job` is still running when its next fire time arrives, APScheduler will not start a second overlapping run of that same job id — the next firing is either skipped or coalesced into one, and a `misfire_grace_time` governs how late a missed firing can still be honored. The one place this is set explicitly is the (unused) prototype scheduler in `sync/database_sync.py`, which sets `misfire_grace_time=60` on its interval job. Given the fixed schedule only fires 4x/day (plenty of headroom) this has never been a real problem in practice, but it's the right thing to name if asked, since it wasn't tuned deliberately — it's the library default.

## 7. How do you avoid re-processing the same shipment data on every run? (Idempotency, watermarks)

Idempotency comes from an **upsert keyed on the CargoWise job number**, not a watermark/timestamp cursor: `services/supabase_service.py:upsert_shipment()` does `supabase.table('shipments').upsert(shipment_data, on_conflict='cargowise_id')`. Every sync re-fetches the whole feed and re-upserts every shipment; there's no "only fetch what changed since last run" — CargoWise's `/cargo-pickup-date` feed doesn't expose a delta/changed-since parameter, so this is a full-refresh model rather than a watermark model. `updated_at` is set explicitly on every upsert (`datetime.now(timezone.utc).isoformat()`) since Postgres/Supabase won't touch it on its own during an upsert.

The milestone side has its own idempotency layer: `shipment_milestones` rows carry a frozen `milestone_snapshot`, and the alert engine's firing history lives in `alert_fire_log` (one row per `(milestone_id, rule_index, occurrence)`), which is exactly what makes `run_alert_engine()` safe to re-run — it only fires occurrences not already logged. Field Watch and the mismatch detector use the same pattern against `sync_errors` (`_already_flagged` / `_already_notified` checks before logging or emailing), so a persistent problem gets reported once, not on every pass.

## 8. CargoWise API goes down for 3 hours. What does your system do? Retries? Backoff? Alerting?

Be honest here — there's no retry/backoff on the CargoWise call itself. `get_access_token()` and `fetch_shipments_from_api()` in `cargowise_service.py` each try once, log the exception, and return `None`/`[]` on any failure (timeout is 30s). `run_sync()` / `run_sync_job()` sees "no data from API," logs it, and simply doesn't update anything that run — the next scheduled firing (next fixed cron time) tries again from scratch. Downstream, nothing breaks: `status_recompute` and the digests just keep working off the last-known `shipments` data, so a 3-hour CargoWise outage quietly shows as "stale but not wrong" data until the next successful pull, rather than a crash.

Where retry *does* exist is Supabase connectivity, not CargoWise: `sales_digest.py` retries transient Supabase network drops up to `QUERY_ATTEMPTS = 3` times with a client reset in between, and `auth_helper._fetch_user_role()` retries a profile lookup once. Sync failures do reach a human: `notify_sync_outcome()` (in `cargowise_service.py`, called from both `run_sync()` and `run_sync_job()`) emails the admins configured in `sync_settings.admin_emails` when the run fails outright, gated by `alert_on_failure`. If asked what you'd add: exponential backoff with a couple of retries on the CargoWise call, and distinguishing "API unreachable" from "API returned empty" in the failure email, since right now both look identical to `notify_sync_outcome`.

## 9. How do you handle partial failures — 80 shipments sync, 20 fail?

Per-shipment, not all-or-nothing. The sync loops shipment by shipment; a single `upsert_shipment()` exception is caught, logged, and counted (`errors += 1`) without stopping the loop for the other shipments. At the end, `status` is computed as `'success'` only if there were zero errors and zero validation issues, `'partial'` otherwise — so 80/20 lands as `status: 'partial'`, `updated: 80`, `errors: 20`, and each individual failure is written to `sync_errors` (job_number, field_name, reason, severity) via `save_sync_error()`, visible on the Sync Management page. If the error count crosses `sync_settings.min_errors_threshold`, `notify_sync_outcome()` emails admins a summary (gated by `alert_on_validation`). Separately, "validation issues" (a null `transport_mode`, a missing pickup date on both the real and AI-derived field) are recorded the same way even on shipments that otherwise upserted fine — so "partial" covers both "some rows threw an exception" and "some rows saved but look questionable."

## 10. What does your sync log table look like? What columns?

One thing to flag up front: the brief calls it `milestone_sync_logs`, but the actual table in the code is named **`sync_logs`**, and it's shared by two different writers with two different column sets — worth reconciling the name before a panel checks the DB directly.

- `services/supabase_service.py:save_sync_log()` (used by the live CargoWise pull in `routes/sync.py` / `app.py`) inserts: `status`, `records_added`, `records_updated`, `error_count`, `total_processed`, `duration_seconds` — and reads back ordered by a `synced_at` timestamp column.
- `sync/database_sync_log.py:start_sync_log()` / `finish_sync_log()` (used by the separate `sync/milestone_sync.py` derivation job) writes a different shape onto the same table name: `sync_type`, `status`, `started_at`, then on completion `total`, `updated`, `created`, `errors` (jsonb array), `error_count`, `finished_at`, `duration_ms`.

So in practice `sync_logs` is a superset table that grew to serve both writers, distinguished mainly by which columns are populated (and `sync_type` when present). There's a companion `sync_errors` table (per-field, per-shipment issue rows: `sync_id`, `job_number`, `field_name`, `error_reason`, `severity`) that the sync-outcome and mismatch-detection paths both write into, using string prefixes on `job_number` (`[new-field]`, `[field-map]`, `[field-delayed]`) to distinguish issue types without needing a separate table per detector.

## 11. If you ran the backend on two servers, would the scheduler run twice? How would you fix that?

Yes — as written, it would. `BackgroundScheduler()` in `app.py` is created and started as part of the Flask app's own process (`scheduler = BackgroundScheduler(); scheduler.start()` at module import time), with no leader-election or distributed lock. Run two instances of this Flask app (two workers, two containers, a second server) and you get every cron job — the CargoWise pull, status recompute, field watch, all three digest jobs — firing twice, which for the digests would mean every sales/ops/super user getting duplicate emails, and for the sync would mean two overlapping upserts (harmless since it's an idempotent upsert, but wasteful and doubles CargoWise API calls).

The fix is to stop running the scheduler inside the web process at all: extract the scheduled jobs into a single separate worker process (or a proper job runner — Celery beat, APScheduler with its `SQLAlchemyJobStore`/a Redis job store, or a cloud scheduler hitting internal trigger endpoints), so however many web servers you run, exactly one process owns the schedule. A cheaper stopgap if you must keep it in-process: a Postgres advisory lock or a "leader" row in Supabase that only one instance holds at a time, and each job checks it before running.

## 12. Explain the Milestone Builder wizard. Why 4 steps?

It's a 4-step wizard (`MilestoneBuilderShell.jsx` orchestrating `Step1_BasicInfo` → `Step2_FieldLinking` → `Step3_AlertRules` → `Step4_Preview`), and the 4-step split maps directly onto the four things you need to decide, and can't decide out of order: what this milestone *is* (name, one of six types — date / missing / document / comparison / status / custom, whether it's critical) determines what Step 2 even asks for; Step 2 links it to real shipment data (a `primary_field`, or `field_a`/`operator`/`field_b` for a comparison, or a `tracking_field` for a document, plus how the due date is computed — `self`, `another_field` + offset, `days_after_creation` + offset, `after_previous_milestone`, or `manual`); Step 3 attaches one or more alert rules (timing, fire condition, recurrence, stop condition, recipient); Step 4 is a plain-English preview before saving. Each step is validated before you can move on (`validateStep()` in the shell — e.g. a comparison type requires `field_a`, an operator, and either `field_b` or a fixed value), so you can't reach Preview with a half-configured milestone. It's the same 4-step builder whether you're creating a reusable Library milestone or building one inline while assembling a template (with an option to also save it to the library).

## 13. "30+ grouped shipment fields" — how did you store a user-defined alert condition in the database? Show me the schema

`FieldSelector.jsx` groups exactly **36 fields across 7 categories** (Date Fields ×13, Status Fields ×7, Consignee Fields ×4, Route Fields ×2, Numeric Fields ×3, Notes & Text ×3, Staff Fields ×4) — the "field" language is deliberate (per the component's own comment) to keep it non-technical for logistics staff, even though under the hood `key` is the literal shipments column/canonical name.

The condition itself is stored as **plain columns on `milestone_library`**, not a generic rule blob — `milestone_type`, `primary_field`, `expected_date_source` / `expected_date_field` / `expected_date_offset`, `document_name` / `tracking_field`, `field_a` / `operator` / `field_b` / `fixed_value` / `threshold_value`, plus `extra_logics` (jsonb array of additional check blocks, added later via `migrations/milestone_multi_logic.sql`) and `logic_combine` (`'and'`/`'or'`). Alert timing lives in a related `milestone_alert_rules` table (rule columns: `timing`, `days_offset`, `fire_time`, `condition`, `condition_field`/`condition_operator`/`condition_value` — added later via `migrations/alert_rule_condition_fields.sql`, `recurrence_type`, `recurrence_interval`, `recurrence_end_type`/`recurrence_end_n`/`recurrence_end_date`, `stop_condition_field`/`stop_condition_type`/`stop_condition_value`, `recipient_type`, `custom_email`).

The part that actually answers "how does the sync know where to find this field's value": `milestone_field_map` (a separate registry table — `milestone_key`, `api_field`, `canonical_field`, `source`, `is_active`) is what `services/field_registry.py` upserts into whenever a milestone is created/edited (`register_milestone_fields()` / `sync_registered_fields()`), and it's what the CargoWise sync reads (`load_field_map()`) to decide which raw API fields to fold into each shipment's `shipments.milestones` jsonb column, under a `canonical_field` name the alert/status logic actually reads (`resolve_field_value()`). RLS on `milestone_field_map` (see `migrations/milestone_field_map_rls.sql`) is enabled but effectively open (`USING (true) WITH CHECK (true)` for select/insert/update/delete) — the backend enforces admin-only writes itself at the Flask layer, not at the database layer.

Finally, when a template is **assigned** to shipments, `routes/templates.py:_snapshot_row()` freezes a copy of the milestone's config (`milestone_snapshot`) and its rules (`alert_rules_snapshot`) directly onto each `shipment_milestones` row — so editing the library definition later never disturbs shipments already in flight.

## 14. What are the three template assignment modes and why three?

`routes/templates.py:preview_assignment` / `assign_template_to_shipments` support: **All** (or, more precisely, by freight mode — `air` / `sea`, filtered on `transport_mode`), **by client** (`by_client`, an `ilike` match on `consignee_name`), and **by branch** (`by_branch`, an `ilike` match on `branch`, matching both a code like "CMB" and a name like "Colombo"), plus a free custom selection of shipment IDs from the picker UI.

One correction to the brief: it describes this as "by shipment type (via country-code detection)" — the code comment in `preview_assignment` explicitly says the opposite: *"we don't have reliable import/export direction data (`st_description` is mostly empty), so assignment is by transport_mode"* rather than country codes. So the real three (four, counting custom) are: freight mode, client, branch, plus a manual selection — the mode was simplified from an original country/direction-based design because the underlying CargoWise data wasn't reliable enough for that. The "why three-ish" answer: freight mode covers the common case (an Air Export template vs a Sea Import template), branch covers "this office handles it differently," client covers "this consignee always needs an extra document check," and custom selection is the escape hatch for anything that doesn't fit a rule. Assignment also has a `conflict_strategy` (`skip` or `replace`) for shipments that already have milestones — `replace` preserves prior progress (status, completed_date, assigned person) for any milestone matched by identity across the re-assignment, so re-running a template assignment doesn't reset work already done.

## 15. Four roles (Admin, Super User, Operations, Sales). How is that enforced in code? What stops Sales from hitting an Admin route?

Answer this one carefully and honestly — the enforcement is real but partial, and that's worth saying plainly rather than overclaiming.

**Authentication**: Supabase Auth issues a JWT on login; `utils/auth_helper.py:get_current_user()` decodes it and looks up the role from the `profiles` table by the token's `sub`. One detail worth naming if pressed: the JWT is decoded with `verify_signature: False` — so the role check trusts the token's claimed identity and looks up the *real* stored role for that user id, but it does not cryptographically verify the token was actually issued by Supabase. In its current form that's a real gap I'd flag as something to fix (verify against Supabase's JWKS/secret) rather than something to gloss over.

**Authorization**: there's no single `@require_role('admin')` decorator applied uniformly. Of the 28 route files, 17 use `require_auth` / call `get_current_user()`, and most of those repeat an inline check like `if 'admin' not in (role or '').lower(): return 403` (seen in `sync.py`, `milestone_library.py`, `system_settings.py`, `field_map.py`, `field_definitions.py`, the three digest routes, `security_settings.py`, `audit_trail.py`, `access_logs.py`). `user_edit.py` / `users.py` add a specific rule on top: a Super User can only create/edit Sales or Operation accounts, never Admin or Super User ones. The remaining ~11 route files (`alerts.py`, `shipments.py`, `milestones.py`, `templates.py`, `dashboard.py`, `department_overview.py`, `custom_tables.py`…) have **no role check at all** — data scoping there is done entirely by `services/scope.py`, which — by its own docstring — currently reads `role`/`email`/`department` **straight from client-supplied query parameters** ("Identity currently comes from the client (mock auth). When real auth is wired, the same params can be read from the verified session instead.").

So the honest answer: for the ~17 routes with an explicit check, a Sales JWT genuinely gets a 403. For the scope-filtered dashboard/alerts endpoints, nothing server-verified currently stops a client from simply passing `?role=admin` in the query string — the frontend's per-role folder structure (`app/(protected)/admin`, `.../sales_user`, etc., each with its own layout providing just the nav chrome, not a role check) and the fact that the UI only ever sends its own user's role are what currently keep this from being exploited in normal use, not a server-side guarantee. This is exactly the kind of gap worth naming under "what would you redesign" — replace `scope.py`'s query-param identity with the identity derived from the verified JWT, and add a real `require_role()` decorator instead of the copy-pasted inline checks.

## 16. What is a Flask blueprint and why did you use them?

A Blueprint is Flask's way of registering a group of related routes (and their own url prefix, if you give it one) as a unit, then wiring the whole group into the app in one `app.register_blueprint(...)` call, instead of every route living in one giant `app.py`. `Backend/routes/` has one blueprint per feature area — `milestones_bp`, `templates_bp`, `milestone_library_bp`, `sync_bp`, `alerts_bp`, `field_map_bp`, `field_watch_bp`, `sales_digest_bp`, and so on — each in its own file, and `app.py` just imports and registers roughly 25 of them. That keeps each teammate's slice isolated (you can hand someone `routes/milestone_library.py` without them touching `routes/auth.py`), makes it obvious where a given endpoint lives, and some are given an explicit `url_prefix` (e.g. `access_logs_bp` → `/api/access-logs`) so the route paths inside the file can stay short. One wrinkle actually in the code worth knowing about: `routes/sync.py` and the unused `routes/database_sync_routes.py` both declare `Blueprint('sync', __name__)` — only `routes.sync`'s `sync_bp` is ever imported into `app.py`, so the name collision never surfaces, but it's a sign the second file is a dead prototype rather than something a second review pass would leave in a clean codebase.

## 17. How many shipments does this handle? What happens at 100,000?

I don't have a real production row count to quote — if asked, better to say that honestly than invent a number. What the code tells you is how it would behave at scale, and there are genuine bottlenecks worth naming rather than claiming it "just scales": `status_recompute.recompute_milestone_status()` and `field_watch.scan_field_alerts()` both do `.select(...).execute()` against the **entire** `shipment_milestones` table with no pagination, then batch-fetch shipments in chunks of 100–200 IDs — fine at hundreds or low thousands of rows, but an unbounded full-table scan every 30 minutes is exactly the kind of thing that degrades badly past 100k rows (memory to hold every row in the Python process, and a single Supabase round trip capped by its own row limits). `services/scope.py`'s per-role shipment-scoping queries have the same shape. The CargoWise pull itself re-fetches and re-upserts the *entire* feed every run (see Q7) rather than only what changed, so its cost scales linearly with total shipment count, not with what actually moved.

What I'd change before 100k rows: paginate the recompute/field-watch passes (process in chunks, e.g. by `updated_at` cursor or ID range), add proper indexes on `shipment_milestones(status, due_date)` and `shipments(job_number)` if they're not already there, and — if CargoWise's API ever exposes a changed-since parameter — move the sync from full-refresh to incremental.

## 18. What would you redesign if you started over?

Grounded in what the code actually shows, not generic answers: give the CargoWise sync a real changed-since/incremental mode instead of re-fetching the whole feed every run; move the scheduler out of the Flask web process into its own worker so it can't double-fire across multiple app instances (Q11); replace `scope.py`'s client-supplied `role`/`email` identity with identity read off the verified JWT, and add one real `require_role()` decorator instead of the ~15 copy-pasted `if 'admin' not in role` checks; verify the JWT signature instead of decoding with `verify_signature: False`; finish wiring `services/alert_engine.py` into a scheduled job and a preview route now that it's built (Q4); rename `sync_logs` → something that matches what's actually documented, or document what's actually there; and paginate the full-table scans in `status_recompute` / `field_watch` before they become a real problem (Q17). None of this is "the design was wrong" — it's the normal gap between a fast-moving student project and a hardened production system, and naming it precisely is a stronger answer than pretending it's not there.
